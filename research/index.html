DESIGNING IN THE OPEN

The making of
Mini Research.

Three practical decisions behind a small home for ideas: show the work, connect real topics, and keep publishing simple.

01 / Show the work first.

The useful takeaway

A one-item collection needs a compelling entry point, not the machinery of a hundred-item catalog. Start with the real work; let navigation grow with the inventory.

Mini Research is a public home for research questions, small websites, and interface concepts. The first version gave its introduction, empty filters, and decorative map too much space. The only article came later. The revised page makes that article the main event.

This note records implementation decisions and reproducible checks. It is design rationale, not a user study: no measured conversion gains, preference findings, or empirical usability claims are implied.

02 / Design decisions.

The visual hierarchy has three jobs: introduce the notebook, make published work unmistakable, and connect its topics. Violet accents tie a dark constellation to light or dark reading surfaces. DM Sans carries the interface; Instrument Serif adds character to the titles. The header follows your system theme or saves an explicit light or dark preference in this browser.

Constraint: moving graph labels are unreliable navigation targets on phones. Choice: a decorative 3D-projected SVG network paired with stationary HTML links. Tradeoff: the graph expresses relationships while the links handle navigation. Unlabelled satellites are illustrative, not extra publications.

The connections mean “topics covered in this field note.” They do not represent extra projects. Future mini-sites and shop prototypes will become entries only when there is real content to open.

03 / Accessibility.

The graph is decorative and hidden from assistive technology. Ordinary links alongside it preserve keyboard navigation, opening in a new tab, and discovery with JavaScript disabled. The animated view has a pause control, starts still when reduced motion is requested, and stops updating offscreen or in background tabs.

Search covers exploration titles, summaries, and connected topics—not the full article body. Results distinguish the exploration from its sections. A query spanning different topics explains that no single section contains every word.

Focus indicators, generous targets, result announcements, and a persistent reading-navigation route support the basic journey. Reduced-motion preferences remove hover transitions. Contents expand by default on wide screens and remain compact on phones. Real screen-reader and physical-device testing are still needed.

04 / Static publishing.

The public site is HTML, CSS, and small enhancement scripts for search, reading navigation, themes, and the graph. There is no server, database, or compilation step. GitHub Actions assembles the intended files and deploys them to GitHub Pages.

index.html          Front door + project catalog
assets/             Styles, search, reading navigation
research/index.html This field note

Project metadata is in the HTML, so the published link exists before scripting. Relative paths support both domain-root and repository-prefix hosting. The tradeoff is manual maintenance: adding an exploration requires a card, topic links, a count update, and an explicitly published folder.

Adding the next exploration

  1. Create a folder with an index.html and its assets.
  2. Add a project card with a unique ID, useful summary, real URL, and search terms.
  3. Link topics to real sections, update the count, and include the folder in deployment.
  4. Check phone and desktop layouts, keyboard navigation, search, and relative links.

A generator may become worthwhile as the collection grows. A static shop prototype can demonstrate browsing and interactions, but real payments, inventory, accounts, and private data require appropriate external services or a backend.

05 / What remains open.

The next useful evidence comes from publishing real explorations and observing their use. Do connected topics help people choose an entry point? Which tags work across research and interface projects? When does manual publishing become awkward?

Those are questions for future observation, not findings established by this design. Source inspection and browser checks establish specific implemented behaviors; they cannot establish that visitors enjoy or understand the experience.
