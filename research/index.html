The making of

01 / A home for the in-between.

Some ideas are too small for a whole product, but too interesting to leave in a notes app. A quick research question. An imaginary storefront. An interactive explanation that makes a tricky concept click.

Mini Research starts with a simple brief: make a public, expandable home for those ideas, hosted as static content on GitHub Pages. Each exploration can have its own visual language and level of ambition. The landing page is the shared front door.

WHAT THESE NOTES ARE

This is a design rationale and a reference trail, not a user study. The choices below are working hypotheses informed by web platform documentation and accessibility guidance. They are not claims of measured improvements or validated user preferences.

The first published exploration is deliberately this one. It gives the collection a real starting point and records the reasoning while the decisions are still fresh.

02 / A map, not just a shelf.

A conventional grid is good at showing a catalog. A map suggests something more interesting: an idea can lead somewhere you did not expect. Research might inspire an interface; an interface might become a tiny shop; building that shop might raise the next research question.

The atlas centers on curiosity. Solid connections lead to published work. Dashed connections point toward possible directions. These edges express a shared origin, not a claim that unpublished projects already exist.

The map is an invitation, not an obstacle. A list view provides the same published links, search, and filters in a simpler arrangement. On narrow screens, the list is the default when JavaScript is available. Search and category state stay the same when switching views.

03 / Quiet structure. Curious details.

The visual direction pairs the looseness of a notebook with the clarity of a small editorial site. The goal is to feel considered without making every experiment feel like a corporate launch.

A warm, open canvas

Off-white surfaces and fine borders let the content breathe. A restrained green marks connections and published work.

Two typographic voices

Instrument Serif brings character to the big questions. DM Sans keeps controls and supporting details readable. System fallbacks keep everything usable if fonts fail.

Meaning before motion

Connections are static. Small hover shifts provide feedback without a constantly moving canvas. Reduced-motion preferences remove those transitions.

Honest empty space

One published page is one published page. Future directions are labeled as possibilities, not dressed up as finished projects.

Accessibility shapes the structure: real links carry navigation, buttons expose their pressed state, search counts use a polite live region, and a keyboard-visible focus ring shows where you are. The SVG connection layer is decorative and hidden from assistive technology. Search is reachable through normal keyboard navigation without capturing character keys.

These are implementation choices, not a blanket accessibility certification. Real-world keyboard, screen-reader, zoom, contrast, and mobile checks remain part of maintaining the site as it grows.

04 / Small enough to understand.

The initial site uses HTML, CSS, and a small JavaScript enhancement. There is no application server, database, or build pipeline. That makes the published output easy to inspect and a natural fit for GitHub Pages.

The live project is present in the original HTML. Its category and search terms sit on the same card as data-category and data-search attributes. This keeps the catalog in one place and lets visitors reach the article even when JavaScript is unavailable.

All internal paths are relative. The same files can live at a domain root or under a repository prefix such as /mini_research/. A GitHub Actions workflow uploads only the public site directories, keeping repository documentation out of the deployed artifact.

What a new exploration needs

  1. A folder with an index.html and any assets it needs.
  2. A semantic project card on the landing page, with a title, summary, category, and search terms.
  3. A connection and position in the atlas, plus an updated published count.
  4. A check that links, search, keyboard navigation, and the mobile layout still work.

This is an intentionally manual starting point. Once several projects exist, a generated catalog may become more maintainable than editing cards and counts directly. Until then, a framework would add more machinery than the collection needs.

A NOTE ON SHOP PROTOTYPES

A static site can host a rich storefront concept, product browsing, and local UI interactions. Real payments, inventory, authentication, or private customer data require appropriate external services or a backend. A prototype should clearly state its limits.

05 / Leave a few questions open.

The useful next step is to add real explorations and watch where this structure becomes awkward. These are the questions worth returning to:

  • Does a map help people discover connections once there are several published projects?
  • Which tags are useful across research, interfaces, and experiments?
  • When does the manual catalog need a generator?
  • Can every exploration keep its own identity while still feeling part of the same place?

Those questions need actual content and observation, not invented statistics. Future field notes can document what was tried, what was checked, and what changed.
